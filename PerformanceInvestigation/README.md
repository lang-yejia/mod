# RimWorld 后期性能：轻量存档检查

记录日期：2026-10-12。此目录不包含原始存档或完整 Mod 列表。

## 方法与边界

运行 `python PerformanceInvestigation/analyze_save.py <存档.rws> ...`，只读取存档 XML，统计每张地图 `<things>` 下的直接对象。脚本不修改存档，也不把尸体内部装备、容器中的物品计为地图独立对象。

这是一轮**结构检查**，不是 TPS 基准测试。对象数量能帮助挑选测试目标，不能单独证明性能影响。三份存档的地形、殖民地规模、游戏版本和 Mod 列表不完全相同，不能把它们之间的差异解释成因果关系。

## 当前判断

1. **优先测试 A 的灰烬/污物清理。** 数量异常高，清理或限制产生源都比较简单。如果处于家园区域，污物还可能产生大量清洁工作。灰烬是否为该存档的主要 TPS 瓶颈尚未测量。
2. **用 C 测尸体清理。** C 有足够多的尸体，适合作对照。若 TPS 变化不明显，就不把自动焚尸或全图清尸作为性能重点。
3. **同时关注活体单位和工作搜索。** 它们可能比静态对象更贵。A 已启用 Performance Optimizer；此次静态检查未见 Dubs Performance Analyzer 或 RocketMan。不要在未测量前叠加更多性能 Mod。
4. **不要直接清理原存档。** 尸体和物品可能影响剧情、财富和资源；大规模删除也会改变后续模拟。实验应在复制存档中进行。

## 下一轮最小运行时对照

选 A 与 C 各一份副本，保持同一游戏版本、Mod 列表、镜头位置和倍速。加载后先等待初始化与短时波动结束，记录至少三段等长的 TPS；随后仅在另一副本中清除目标对象，再重复记录。A 分别比较“仅灰烬”“全部污物”，C 比较“仅尸体”。每次只改一个变量，保留原始副本。

若差异小于正常波动，停止清理方向；改用 Dubs Performance Analyzer 定位 Tick、工作搜索或界面耗时。该步骤需要实际启动游戏，当前报告未宣称任何 TPS 提升。

## 第二步：已准备的运行时对照（2026-10-12）

选择 B，是因为它的 11 个 Mod 与本机当前启用的 Mod 列表和顺序完全一致，可以避免为实验切换配置。用 `make_filth_pair.py` 在游戏 Saves 目录生成了 `Codex-Perf-B-baseline.rws` 与 `Codex-Perf-B-no-filth.rws`；后者仅从地图 `<things>` 中删除 3,076 个 `Filth` 对象。两份副本再次解析成功，地图对象数分别为 10,688 与 7,612。原始存档未更改；实验副本未上传 GitHub。

游戏窗口第一次被用户手动最小化，随后重新选定正确的 RimWorld 窗口并恢复控制。**两份实验副本都已在游戏中成功加载**；清理版运行后的日志未见加载异常。原始存档始终未被修改。

以相同画面、游戏三倍速进行一次约 20 秒的短测，记录进程 CPU 用时：基准版 28.52 CPU 秒 / 20.03 墙钟秒，清理版 27.38 CPU 秒 / 20.04 墙钟秒。清理版低约 4%，但只有一次短样本，包含绘制、单位活动和系统负载变化，**不足以认定有性能收益**。

曾尝试通过运行后存档的 `ticksGame` 计算 TPS；这次加载后游戏在正式计时前已经运行，无法得到一致的起始刻数，因此不采用该数字。下次若继续，应在两份副本中先暂停并各保存一个起点，再采用相同的开始/停止计时流程；或使用游戏内 TPS 工具直接读数。当前结论是：清除 3,076 处污物没有表现出显著到可由这次短测确认的收益。
